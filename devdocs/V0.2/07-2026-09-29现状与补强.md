## 3. 本轮对计划的实质补强

### 3.1 把现状统计变成可比较的基线

**B-01/B-05/A-05** 不只记录源码 hash：同时冻结目标平台、构建 feature、可执行与库目标的分母、默认/显式/direct 路由、每个 canonical digest、拒绝阶段、构建失败原因、每个 legacy owner 的实际消费者及删除条件。未来的 0.2 趋势至少给出 whole-program route、已准入操作覆盖、公开 stdlib 完整调用图三条曲线；Resolved emitter eligibility 只作迁移诊断。`--zero` 对 legacy fallback 的严格失败保留，不能为了好看的绿色而从语料中排除两个 Actor 样本。

### 3.2 从专用 MapRoot 跨到普通生产 Map/Any

**V-11** 是 V-02～V-06/V-10 的生产整合任务。允许先按 payload/调用形状逐步实现，但 0.2 发布验收必须覆盖普通 API 与 `Option`/`Result`/List/记录/泛型/闭包组合中实际暴露的所有权路径。先定义 Any 的类型描述与 owner token、Map entry 的拥有/借出/快照身份、clone 与代际规则，再把 `set/get/values/remove/clone/destroy`、覆盖和失败边变成 Checker receipt 与 MIR 验证对象。对同一 MIR 跑四消费者、伪造 receipt 负测、默认/direct/CLI route，并在**普通生产路径**跑内存工具。析构可以触达其他 runtime registry，因而须用重入、跨线程、失败注入证明锁序；最近的锁外析构改动是必要基础，尚不是这项验收。

### 3.3 把 Actor/Flow 作为真正的 native 语言能力

**F-09** 为 Actor `runs Flow` 的持久状态、mailbox、字段 effect 和合成转移定义身份，并为 nested capture/shadow 定义环境 ABI/生命周期。保留显式同名 Actor 方法的分派优先序；包含 `self` 调用、独立 Flow 调用、失败、取消和多 Actor 交错的正反矩阵。目标图的 `E0722` 正例与两条 compatibility fallback 消失后，才可称 VM/native 同义。只修错误消息不算 F-09 完成。

### 3.4 FFI 导出体和验证器必须跟着同一事实走

**M-09/E-06** 把 scalar C import、Mimi C export 与外部 C 库分成三个身份。导出体需要可检查的 MIR wrapper/body ABI、受信摘要、内部递归与调用所走符号、外部可见符号、错误与资源转移；无 `main` 的库项目按库目标构建和测试。验证器在所有 callable 和初始化位置扫描 FFI obligation，并在默认、显式 MIR、direct API、`--dump-z3` 维持一致结论。已知简单 `bool` 合同分歧须以原样例修成一致正确结论，不能通过替换测试类型或移出必需受信子集消失；复杂公式的受信边界另行裁决。

### 3.5 旧 owner 的退出是逐边证明，不是一个总数

现存 `CodegenLegacyRemainder`、`FlowVerifierCompatibility`、`FfiVerifierCompatibility`、`DualVerifierCompatibility` 各自记录 `accessor → 调用条件 → 目标图可达性 → 替代 MIR consumer → 物理删除`。A-05 在所有 0.2 必需路径上要求零隐藏 compatibility；旧 owner 若仍服务图外历史能力，准确标识隔离边界，不把它计作已退休。每个新增 profile 的 receipt 同时指出它替代哪条生产旧边，避免只增岛、不减权威。
